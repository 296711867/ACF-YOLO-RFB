## 2. 为什么每个 epoch 约 22.6 分钟

| 因素 | 数值 | 影响 |
|---|---:|---|
| 完整训练集 | 70,000 张 | batch16 时每 epoch 4,375 个训练 micro-batch |
| 完整验证集 | 10,000 张 | 每个 epoch 另有 625 个验证 batch |
| 输入像素 | 960² vs 640² | 单图像素和主要计算量约 2.25 倍 |
| P2 输出 | 240×240 网格 | 高分辨率检测层的激活和双检测头开销大 |
| YOLO26 end-to-end | one-to-many + one-to-one | 训练期同时计算两套检测分支 |
| 梯度累积 | batch16、nbs64 | 每 4 个 micro-batch 更新一次；保持约 1,094 次优化器更新/epoch |

P2-640 正式训练平均 10.51 分钟/epoch；P2-960 实测 22.68 分钟/epoch，比例 2.16 倍，与像素/GFLOPs 比例 2.25 倍基本一致。因此当前速度不是程序卡死或 GPU 未吃满，而是分辨率和数据规模的正常计算成本。

200 epoch 外推约 75.6 小时；已完成 14.74 小时，原计划仍需约 60.9 小时。

## 3. 决策复盘

从工程计算看时长合理，但从研究资源管理看，短跑通过后直接启动 200 epoch 过于激进。更合理的流程应设置 20/40/60 epoch 阶段门，在每个门点评估收益曲线和尺寸指标，再决定是否继续。当前 epoch 39 的 mAP50-95 已达到 0.28507，超过 P2-640 200 epoch 的 0.26871；继续 161 epoch 很可能以大量时间换取较小边际收益。

## 4. 最终决策

用户已决定不再恢复P2-960到200 epoch。P2-640继续作为论文主模型，P2-960 epoch39仅作为计算预算受限的分辨率实验。下一步只做一次完整10k val独立/尺寸评估，评估完成后关闭该工作包。

原建议与备选如下，现仅保留作决策依据：

推荐暂不恢复 200 epoch，先对 epoch 39 best 执行完整 10k val 的独立验证和 small/medium/large 评估。该评估只需推理，不进行反向训练，可直接判断当前模型是否已经满足论文结论。

后续选项：

1. **推荐：停在 epoch 39 做完整评估。** 若尺寸指标已经明显优于 P2-640，则把它作为“计算预算受限的 P2-960 阶段结果”，诚实注明训练轮数。
2. **严格公平：精确恢复到 200 epoch。** checkpoint 完整，但还需约 61 小时。
3. **效率模型：从已收敛 P2-640 best 在 960 上渐进微调 10–20 epoch。** 预计约 4–8 小时，但这是新的训练策略，不能冒充原始 200 epoch 消融。

最终选择第1项；第2、3项当前均不执行。

不建议直接重启一个新的 50 epoch 960 训练：那会丢弃已经投入的 14.7 小时，而且学习率计划不同，不能与当前 checkpoint 无缝拼接。
